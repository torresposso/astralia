Words are architecture: ubiquitous language

A rename is not a cosmetic change. The words you use in code, conversations, and docs are the architecture of understanding.

1 · Hook — a question before any jargon

You and a chef are writing a recipe together. You say "dough" — you mean money. The chef says "dough" — they mean flour paste. You write "add the dough", the chef adds flour, you lose the money. Who is wrong? Nobody — the shared vocabulary was wrong.

Software teams live this every day. The business says one thing, the code says another, the docs say a third, and the AI confidently mixes all three. DDD's answer is a ubiquitous language: one shared vocabulary that everyone — humans and code — actually uses.

By the end of this lesson you will know what ubiquitous language is, and you will be able to judge an AI rename as a domain-language decision, not a cosmetic refactor.

3 · The concept in small steps

New words this lesson: 5

  • Ubiquitous language — the shared, context-specific vocabulary used by domain participants and code.
  • Vocabulary contract — the document (here, CONTEXT.md) that fixes terms and forbidden synonyms.
  • Overloaded name — one word used for several different roles.
  • Stale documentation — docs that describe an older model than the code.
  • Model drift — a term's meaning silently changing while the code moves on.

Step 1 — One shared dictionary

In plain words: ubiquitous language is the team dictionary: the same words for the same things, used in conversation, in docs, and in code.

Precise definition: ubiquitous language is the shared, context-specific vocabulary used by domain participants and represented consistently in conversations, documentation, and code. It is not a translation table or a UI copy list.

The analogy — a team dictionary: every sport has one. Players and coaches both read it: "offside" means exactly one thing, so a referee's call is understood instantly. Code identifiers become entries in that dictionary: BirthData means one thing, everywhere, to humans and to the AI.

Where this analogy stops being true

A printed dictionary is frozen; a ubiquitous language evolves as the business learns. It also has a local scope: the same word can mean different things in different bounded contexts — which is why the dictionary is per-context, not global.

What is ubiquitous language?

Step 2 — One word, many roles: the overload trap

In plain words: when one name is used for several different jobs, the word stops carrying meaning and starts carrying confusion.

Precise definition: overloading — reusing one identifier for distinct concepts — makes model drift invisible, because a rename or a new rule touches "the same word" in places that mean different things.

The analogy: your house key and your office key look similar, but they open different doors. Calling both "the key" works until one day you need to cut a new one — for which door? In Astralia, the family BirthData plays several roles: BirthData.vo.ts (the domain value object), BirthDataInput in SaveBirthData.ts (the route payload), BirthDataCard.astro (a UI component), and the api/birth-data/ routes (HTTP). Same word, different roles — and each role can change independently.

Where this analogy stops being true

Keys are physical objects; names are free. We could rename one role tomorrow — and sometimes we should. The discipline is not "never overload", it is "notice the overload and decide on purpose".

Why is BirthData used so often?

Step 3 — The vocabulary contract: CONTEXT.md

In plain words: the team writes the dictionary down — term, meaning, context, and the forbidden synonyms — so everyone can check before they speak or code.

Precise definition: a vocabulary contract fixes the ubiquitous language for a bounded context, listing terms, their meanings, the real code symbols, and the synonyms to avoid; it is the authority against which renames are judged.

The analogy: a constitution. Laws (terms) are written down, and when there is a dispute you read the constitution, not what someone remembers. In Astralia, CONTEXT.md is that document: for each term it gives the meaning and an _Avoid_ list (e.g., Avoid: Dato de nacimiento for Birth Data, Avoid: Login for Sign In).

Where this analogy stops being true

A constitution is hard to change; a vocabulary contract must be easy to update when the business changes. And like any document, it can go stale — which is why the code is the final witness when docs and code disagree.

4 · Worked example — I do

I will audit the vocabulary of one Astralia term out loud. Read with me: CONTEXT.md and the code it claims to describe, src/domain/chart/ports/IChartCalculator.ts.

"First I open CONTEXT.md and I look at the Chart Calculator entry (it is written in Spanish). It says: 'Domain Service (interface IChartCalculator) that, given Birth Data in UT and calculation options, produces a NatalChart.' One label: a domain service. Good — now I check the code.

  • "The port IChartCalculator lives in the domain, as a contract should. But who implements it? CaelusChartCalculator — and that class sits in src/infrastructure/chart/ and wraps the caelus library. An implementation in infrastructure that satisfies a domain port is an adapter, not a domain service (Lesson 06)."
  • "So the contract's label and the code disagree. Which source is authoritative? The code and the architecture tests, not the prose. The entry's words drift from the code's real role — that is model drift, and catching it is the skill."

"What I noticed: the contract's label is stale; the code is the ground truth. When the AI proposes a rename, I now know to ask: which document says what, and what does the code actually do today?"

My evidence-based note: "CONTEXT.md calls CaelusChartCalculator a domain service, but the class lives in src/infrastructure/chart/ and implements the IChartCalculator port — that is an adapter. The doc label drifts; the code and tests/architecture.test.ts are authoritative."

5 · Guided practice — we do

Three vocabulary questions, with less help each time. Answer before opening the suggestion.

Q1 — worked with me. Open CONTEXT.md. In which bounded context does the term NatalChart live, and what does the contract say it is?

My reasoning: the term says "natal chart", and the code symbol is NatalChart.vo.ts under src/domain/chart/. The contract describes it as the chart of a person's birth moment — that is the Chart context. Answer: Chart context; "the specific type of Chart that represents the natal chart of a person at the moment of their birth".

Answer 1 — check after you try

Chart. The contract defines NatalChart as the Value Object of the domain containing planets, angles, houses, aspects, and additionalPoints — immutable, calculated by IChartCalculator.

Q2 — half-worked. What does the term whole-sign mean in the contract, and what code symbol emits it?

Starter of the reasoning: CONTEXT.md explains Whole Sign as the house system used when birth time is unknown. Now find where the warning is emitted — search for the string in SaveBirthData.ts or warnings.ts…

Answer 2 — check after you try

Whole Sign = the house system used when Birth Time is unknown; every house cusp equals the sign degree, and a warning is displayed. The code symbol is the 'whole-sign' member of WarningCode, pushed by SaveBirthData when the saved record has no time.

Q3 — your turn to finish. The contract lists the term toUT under _Avoid_ for CaelusBirthConverter, yet the port file is named IBirthToUTConverter.ts. Is that a contradiction, or a language decision?

Start: read the Avoid line: it says to avoid the shorthand "toUT" and the generic "Caelus converter". The full term in the contract is "Universal Time (UT)". Now complete the last step: the file name is the real symbol, but the language contract says the preferred name is ______ — and when a rule changes, you should update the ______, not the file, unless the rename is agreed by the team.

Answer 3 — check after you try

Not a contradiction — a decision. The contract prefers the full phrase "Universal Time (UT)" and the specific name "CaelusBirthConverter", while flagging "toUT" as shorthand to avoid in speech and docs. Real symbols can lag the contract; the contract is what you use to notice and fix the drift.

7 · Feedback + wrap-up

You should now be able to say:

  • "CONTEXT.md is the vocabulary authority; the code is the final witness when docs disagree."
  • "BirthData is an overloaded name — I can list its roles without renaming anything."
  • "A rename is a domain-language decision; I judge it with the contract, not with taste."

Where the dictionary analogy breaks (recap): dictionaries are static and global; ubiquitous language evolves and is scoped per context, and the contract itself can go stale — always verify against the code.

Next lesson: with the language fixed, we classify the things it names — identity versus description (entity vs value object).

Spaced question to remember: "Is a rename cosmetic? — No: it is a language decision, judged against CONTEXT.md and the current code."

AI Drill — try it with the AI

Ask your assistant: "Should SaveBirthData become CreateBirthDataUseCase?" Require an answer that names the context, describes the current behavior (create() and update() over a private save()), and weighs the cost of changing the language before deciding. If it renames "because it's cleaner", veto it with the evidence: the module handles both create and update today.
