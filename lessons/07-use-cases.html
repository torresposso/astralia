User goals become use cases: the application layer

Someone must run the show: load, decide, save, respond. That someone is the use case — and it never decides the recipe.

1 · Hook — a question before any jargon

You order pasta in a restaurant. The waiter takes the order, walks to the kitchen, and later brings the plate. Who decides the recipe — the waiter or the chef? And who would you blame if the pasta arrives cold or with the wrong ingredients?

The waiter orchestrates: they move the order from table to kitchen and back, and they do not cook. The chef decides: recipe, portions, quality. Software needs the same separation — a coordinator for each user goal, and business rules living with the domain, not scattered in the transport layer.

By the end of this lesson you will be able to trace any API route to its use case, and demand that business rules never live directly in HTTP handlers.

3 · The concept in small steps

New words this lesson: 4

  • Use case — an application-level coordinator for one user goal.
  • Application service — another name for the same coordinator.
  • Orchestration — running the sequence: load, decide, save, respond.
  • Domain service — a business rule that does not live in one object (Astralia has none yet).

TS basics — a function is a recipe

A function is a named set of steps that turns inputs into an output and can be reused. The analogy (from Samer Buna at freeCodeCamp): a recipe — ingredients in, dish out, same steps every time. A program is a recipe book; the computer is the cook.

Where this stops being true: recipes do not call other recipes with promises and errors. Functions can return async values, fail halfway, and call other functions — a recipe cannot. The idea that survives: steps in, result out, reusable.

Step 1 — The use case: one goal, end to end

In plain words: a use case is the coordinator that runs one user goal end to end: load what you need, decide, save, respond.

Precise definition: a use case (application service) coordinates one user goal, calling domain objects and ports in the right order; it is not the place to dump business rules or infrastructure details.

The analogy — the waiter vs the chef: the waiter runs the order; the chef decides the recipe. In Astralia, SaveBirthData is the waiter: it validates via BirthData.create() (the chef), gates the UT conversion through IBirthToUTConverter (ordering from the pantry), and persists through IBirthDataRepository.

Where this analogy stops being true

A waiter serves one table at a time; a use case can be called by several routes and can return rich results. Also, waiters are replaceable — use cases carry real policy (the DST gate), so they deserve their own tests, not just the routes' tests.

What does a use case orchestrate?

Step 2 — Orchestrating vs deciding

In plain words: the use case runs the show, but the domain makes the business decisions.

Precise definition: orchestration is sequencing — load, validate, convert, persist, map; decisions — whether an operation is legal and what it means — belong to domain objects and domain policy.

The analogy — the ATM (Khorikov): the application service orchestrates: it checks the balance (a decision made inside the entity), dispenses cash, charges the gateway, saves. The domain makes the business decisions; the app service runs the show and talks to the outside world.

Where this analogy stops being true

An ATM is a physical machine with one job. Use cases are code that can grow fat if no one watches: every "while I'm here, let me also …" pushes a rule into the coordinator. The discipline is "why-to-change": rules go to the domain, sequence stays here.

Who decides the business rules?

Step 3 — Domain services: a rule without a home (yet)

In plain words: sometimes a business rule does not naturally live in one object — it applies between objects. DDD calls that a domain service: a referee applying a rule between players.

Precise definition: a domain service is a domain-layer object expressing a business policy that does not fit inside a single entity or value object; it depends only on domain concepts.

The analogy — the referee: a referee does not play; they apply the rule between players. In Astralia the best candidate is the DST policy (nonexistent / ambiguous / ok) — a rule that lives between the birth data and the UT conversion.

Where this analogy stops being true

Referees are impartial humans with whistles; domain services are code objects that must be tested like any rule. And beware the naming trap: CaelusChartCalculator is NOT a domain service — it lives in infrastructure and implements the IChartCalculator port. It is an adapter (Lesson 06 material), not a domain object. Astralia has no pure domain service yet.

4 · Worked example — I do

I will trace three real flows from HTTP route to use case to port, out loud. Follow the reasoning; you will write one card yourself.

  • src/pages/api/auth/signin.ts → src/application/auth/SignIn.ts
  • src/pages/api/birth-data/create.ts → src/application/birth/SaveBirthData.ts (its create() and update() both run the private save())
  • src/pages/api/chart/natal.ts → src/application/chart/CalculateChart.ts

"First, signin. The route receives email and password. It does NOT validate them itself — it builds a SignIn use case and calls execute(). Inside SignIn: validate Email.create, validate Password.create (domain objects decide), then authRepo.signIn (a port), then map the result. Given an email and password; when execute() runs; then it returns ok with redirectTo and cookies, or an error.

"Second, birth-data/create. The route maps the HTTP body via toBirthDataInput, then SaveBirthData.create() or update() — both funnel into private save(). SaveBirthData validates with BirthData.create (rule), gates the UT converter (port), and persists via the repository (port). It returns typed warnings. Now, who turns the warning code 'whole-sign' into a Spanish sentence? Not SaveBirthData — the interface layer, in responseMapping.ts. That file maps WarningCode to UI strings and errors by their typed discriminant."

"Third, chart/natal. The route calls CalculateChart, which loads birth data through IBirthDataRepository, converts through IBirthToUTConverter, and calculates through IChartCalculator — the port whose adapter is CaelusChartCalculator. The use case coordinates; the adapter does the astrology."

What I noticed: every flow has the same skeleton — route (transport) → use case (orchestration) → domain objects decide → ports → adapters → result mapped at the interface. When the AI wants to put persistence in a route, it is skipping the skeleton.

5 · Guided practice — we do

Three questions toward your own use-case card, with less help each time. Answer before opening the suggestion.

Q1 — worked with me. Write the Given/When/Then for the sign-in flow.

My reasoning: Given a valid email and password (the inputs); when SignIn.execute() runs; then the repository signs the user in and the use case returns { ok: true, redirectTo: '/dashboard', cookies } — or, if credentials are wrong, { ok: false, error }. Notice the decision "is this email well-formed?" happens in the domain objects, not in the route.

Answer 1 — check after you try

Given an email and password; when SignIn.execute() runs; then Email and Password are validated in the domain, the auth repository authenticates through the port, and the result (redirect + cookies, or an error) is returned to the route.

Q2 — half-worked. Who decides that a nonexistent local time is an error, and who merely runs the check?

Starter of the reasoning: read SaveBirthData step 3: the converter returns a status ('ok' | 'ambiguous' | 'nonexistent'). Complete the thought: the ______ returns the status (a mechanism), and ______ applies the policy: nonexistent → reject, ambiguous → warning.

Answer 2 — check after you try

The UT converter (IBirthToUTConverter) computes the status — a mechanism; SaveBirthData applies the DST policy — reject on 'nonexistent', warn on 'ambiguous'. The decision lives in the use case, which is why the use case needs its own tests.

Q3 — your turn to finish. Why do the UI strings live in src/pages/api/birth-data/responseMapping.ts and not inside SaveBirthData?

Start: SaveBirthData returns typed codes (WarningCode[], typed errors). Complete the last step: the use case speaks ______ (codes and types); the interface layer speaks ______ (HTTP and user-facing strings); keeping them apart means the domain never knows about ______.

Answer 3 — check after you try

The use case speaks domain language (typed codes); the interface layer speaks HTTP and user-facing strings. Keeping them apart means the domain and application never know about UI text — the exact reason responseMapping.ts exists and warns are translated there.

Hints:

  • The Given is the HTTP body mapped by toBirthDataInput; the When is SaveBirthData.create() (or update()); the Then is the typed output plus the response built by responseMapping.ts.
  • Domain concepts: BirthData, WarningCode, the DST policy. Ports: IBirthDataRepository, IBirthToUTConverter.
  • Result mapping: warnings become UI sentences; errors become HTTP status codes by typed discriminant — never by string matching.

Tangible win

A use-case card that makes orchestration and business policy visibly separate — the proof you can place a new rule by reason-to-change, not by guesswork.

7 · Feedback + wrap-up

You should now be able to say:

  • "A use case coordinates one user goal through ports; domain objects decide the rules."
  • "I can trace signin, birth-data, and chart flows from route to use case to port."
  • "CaelusChartCalculator is an adapter, not a domain service; Astralia has no pure domain service yet."

Where the waiter/chef analogy breaks (recap): waiters are interchangeable and carry no policy; use cases carry real policy (the DST gate) and need their own tests.

AI Drill — try it with the AI

Veto any design that puts business rules or Drizzle imports into the route.
