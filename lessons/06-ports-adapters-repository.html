Contracts inward, technology outward: ports, adapters and repository

The domain declares what it needs; the outside world plugs in how it is done. This lesson makes vendor swaps predictable instead of scary.

1 · Hook — a question before any jargon

Your laptop has a USB-C port. Does the laptop care whether the charger is Apple, Samsung, or a generic brand? No — the port defines the shape, and any plug that fits works. Now imagine the opposite design: a laptop that is welded to one specific charger, with its cable glued in. To change chargers you would have to rebuild the laptop.

Software does this all the time: business logic welded to a specific database, a specific HTTP framework, a specific astrology library. DDD's answer is to draw the port (the socket) and write adapters (the plugs).

By the end of this lesson you will be able to trace any Astralia port to its adapter, state who owns the contract, and predict what changes when a vendor changes.

3 · The concept in small steps

New words this lesson: 4

  • Interface / contract — a promise of actions an object provides.
  • Port — a contract owned by the inner layer for a needed capability.
  • Adapter — an outer implementation that satisfies a port.
  • Repository — a collection-like persistence port.

TS basics — what is an interface?

An interface is a promise: "anything that claims to be X must provide these actions." In TypeScript, interface IBirthDataRepository lists the methods (create, findById, update, delete) and the types they use. The promise has no body — the implementation lives elsewhere.

The killer analogy (from tiberriver256): a tool has a 6×2-inch rod spec. The arm-team and the whacker-team build separately, but because both follow the spec, the rod makes them fit. The spec is the interface; neither team needs the other's code.

Where this stops being true: a spec can be followed wrongly. An interface guarantees the shape, not the behavior — behavior is proven by tests (Lesson 10).

Step 1 — The port: a socket owned by the inside

In plain words: a port is a hole with a fixed shape — the contract for a capability the domain needs but does not implement.

Precise definition: a port is an interface owned by the domain or application layer that declares a needed capability without saying how it is fulfilled; the outside world supplies the fulfillment.

The analogy — the USB-C socket: the socket speaks one language (voltage), and any charger adapts to it. The application core (the socket) never changes when devices (database, HTTP, tests) plug in. Cockburn invented the name from electronics ports.

Where this analogy stops being true

Sockets have a fixed standard; ports are shaped by your own design decisions and can change when the business changes. Also, a socket does not care who owns it — ownership is the whole point of a port: the inner layer owns the contract, never the vendor.

What does an interface promise?

Step 2 — The adapter: the plug for one device

In plain words: an adapter is the plug that makes one specific device fit the port — it translates the outside world into the contract.

Precise definition: an adapter is an outer-layer implementation or translator that satisfies a port, converting the port's language into the vendor's API and back.

The analogy: a universal travel adapter — the wall socket is a port; each country's plug is an adapter for its own power grid. In Astralia, CaelusBirthConverter implements IBirthToUTConverter: the domain says "convert this birth data to UT", and the adapter knows how to speak to the caelus-birth package.

Where this analogy stops being true

Adapters in code are not interchangeable hardware: each one may have different failure modes and different results. Swapping an adapter is safe for the contract, but the behavior behind it still needs its own tests.

Who owns the port contract?

Step 3 — The repository: a collection you can ask

In plain words: a repository is a box with a label: you ask for "birth data with id X" and get it back, without knowing if it came from a shelf, a vault, or a warehouse.

Precise definition: a repository is a collection-like interface for loading and saving domain objects, acting like an in-memory collection while hiding the storage technology. It is one kind of port — not every adapter is a repository.

The analogy — the library catalog/librarian: you ask the librarian for a book by title; you never walk into the storage room. The library can reorganize the whole warehouse and you do not care. In Astralia, IBirthDataRepository is the label; DrizzleBirthDataRepository is the warehouse worker.

Where this analogy stops being true

A library catalog is read-only and well organized; repositories handle writes, failures, and tricky consistency questions. A repository also does not make everything an aggregate — as Lesson 05 showed, persistence of a unit does not prove a root.

4 · Worked example — I do

I will trace every Astralia port to its adapter out loud. The ports live under src/domain/*/ports/; the adapters under src/infrastructure/.

"First I look at IGeocoder. It declares a capability: resolve a place name to coordinates and timezone. Who knows Open-Meteo's API? Not the domain — the adapter. If tomorrow we switch to a different geocoding service, the port, the domain, and the use cases stay untouched; only OpenMeteoGeocodingAdapter changes. That is the answer to 'what remains unchanged?': everything inside the port."

What I noticed: every row has the same shape — inner contract, outer plug, vendor knowledge contained at the edge. The blast radius of a vendor swap is exactly one adapter.

5 · Guided practice — we do

Three questions, with less help each time. Answer before opening the suggestion.

Q1 — worked with me. For IBirthDataRepository → DrizzleBirthDataRepository: who owns the interface, and who knows the vendor (Turso + Drizzle)?

My reasoning: the interface file lives in src/domain/birth/ports/ and uses only domain types (BirthData, domain errors). The implementation file imports the database client and writes Drizzle queries. So: the domain owns the interface; the adapter knows the vendor.

Answer 1 — check after you try

Domain owns the interface; DrizzleBirthDataRepository knows the vendor. The location (domain/ports vs infrastructure) and the imports are the evidence.

Q2 — half-worked. If Astralia swapped Turso for PostgreSQL, what must stay unchanged?

Starter of the reasoning: the contract is the port. Ask: who depends on the port — the domain and the use cases. Complete the thought: only the ______ changes; the domain, the use cases, and the ______ stay untouched.

Answer 2 — check after you try

Only the adapter (DrizzleBirthDataRepository or a new Postgres adapter) changes. The port, the domain objects, and the application use cases stay untouched — that is the point of the seam.

Q3 — your turn to finish. For IChartCalculator → CaelusChartCalculator: if the team adds a second chart calculator, what changes and what does not?

Start: the port lists calculate(...) — one capability. A second calculator would be another class implementing the same port. Complete the last step: the ______ stays; the new calculator is a new ______ that implements the same ______; the application policy that calls it does not change unless the contract itself grows.

Answer 3 — check after you try

The port stays; the new calculator is a new adapter implementing the same contract; the application policy stays unchanged unless the contract grows. You predicted the Lesson 08 placement task — that is the pattern doing the work.

6 · Independent practice — you do

Build the inward/outward dependency map. Copy the five rows from the worked example into your notebook, then for each row answer the three questions:

  1. Who owns the interface?
  2. Who knows the vendor?
  3. What should remain unchanged when the vendor changes? (name at least one concrete file)

Verify each answer by opening the actual files: check the folder, the imports, and which types appear in the interface signatures.

  • IAuthRepository.ts vs BetterAuthRepository.ts
  • IBirthDataRepository.ts vs DrizzleBirthDataRepository.ts
  • IBirthToUTConverter.ts vs CaelusBirthConverter.ts
  • IGeocoder.ts vs OpenMeteoGeocodingAdapter.ts
  • IChartCalculator.ts vs CaelusChartCalculator.ts and CaelusChartMapper.ts

Then draw it as a map: the ports in one ring (inner), the adapters in the outer ring, with arrows showing who depends on whom. Mark any row where the adapter imports a vendor SDK (e.g., caelus, Drizzle, better-auth) — those are the seams.

Tangible win

An inward/outward dependency map — show it to the AI before any vendor change and demand the plan touches only the adapter ring.

7 · Feedback + wrap-up

You should now be able to say:

  • "Every Astralia port has an adapter; the domain owns every contract."
  • "A vendor swap changes exactly one adapter — I can name the file."
  • "A repository is a kind of port; not every adapter is a repository."

Where the USB-C analogy breaks (recap): ports are your design, not a standard; adapters are not interchangeable hardware, and their behavior still needs tests.

Next lesson: who calls these ports? User goals become use cases — the application layer that orchestrates everything.
