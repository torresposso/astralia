Identity versus description: entity and value object

One object is who; the other is what. The difference decides whether you add an id, a setter, or a repository.

1 · Hook — a question before any jargon

Which one are you: a person or a $5 bill? You have an identity — you are still you at age 5 and age 50, though every cell in your body has been replaced. A $5 bill is just $5: swap it for another $5 bill and nothing changed. One is a who, the other is a what.

In code, this difference decides everything about how you design an object: does it need an id? Does it change over time? Can two of them be the same? Teams that ignore it turn every concept into a table with a primary key — and lose the meaning.

By the end of this lesson you will be able to classify any object as an entity or a value object, and veto AI proposals that add IDs or setters to descriptions.

3 · The concept in small steps

New words this lesson: 4

  • Entity — a thing with a lifelong identity.
  • Value object — a description defined by its values, normally immutable.
  • Identity — what makes an object itself over time.
  • Immutable — cannot change after creation.

Step 1 — The entity: a lifelong identity

In plain words: an entity is a thing with a stable identity — it stays "itself" even when its details change.

Precise definition: an entity is an object recognized by a stable identity that persists through time and through changes in its attributes; two instances with the same identity are the same thing.

The analogy — a person: you have an id that follows you your whole life. Change your haircut, your job, your address — still you. In Astralia, User is the entity: two User instances with the same id are the same person, and User.equals() compares by id, not by name.

Where this analogy stops being true

A person's identity is a fact of the world. In code, identity is a choice: you decide which field is the id, and the id only matters if the object has a lifecycle — it is loaded, changed, and saved again.

What makes something an entity?

Step 2 — The value object: the description is the thing

In plain words: a value object is a description where the value itself is all that matters — two equal descriptions are the same description.

Precise definition: a value object is an object defined by its values, not by identity; it is normally treated as immutable and replaceable — swapping one for an equal one changes nothing.

The analogy — money: two $5 bills are the same $5. Your pet is an entity (it has a name and a life); its name tag is a value object — two identical tags are the same tag. In Astralia, Email is a value object: an email address has no identity beyond its characters. The validated string is the email.

Where this analogy stops being true

Bills have serial numbers — real money does have an identifier. A value object must not: if you start tracking each bill by serial number, you have accidentally turned a description into an entity. That is exactly the trap the AI drill at the end exposes.

How are value objects compared?

Step 3 — Immutability: the value object's promise

In plain words: a value object never changes after it is created; to "change" it, you make a new one.

Precise definition: immutability means the object's state is fixed at creation; any operation that would alter it returns a new instance instead. This keeps equal values truly interchangeable.

The analogy: a printed ticket. You cannot erase and rewrite the seat number on the ticket; you print a new ticket. In Astralia, BirthData.vo.ts uses a private constructor and exposes getters — no setters — so a birth record is born valid and stays that way.

Where this analogy stops being true

Tickets get torn and replaced constantly; value objects in memory can be held in many places at once. If you mutate one and it is shared, you corrupt everyone — immutability is a safety promise, not a natural law of paper.

4 · Worked example — I do

I will classify two real files out loud. Read with me: src/domain/auth/User.entity.ts and src/domain/auth/Email.vo.ts.

"First I open User.entity.ts. The comment at the top says it all: 'Identity is the id field — two Users with the same id are the same User.' I check equals(): it compares this.id === other.id. Identity. And it has behavior — canSignIn(), getInitial() — so it is not just data. Classification: entity, with evidence: the id field and the identity-based equals().

"Now Email.vo.ts. I look for an id field: there is none. I look for what makes two emails equal: the characters. The class validates and exposes the value; there is no lifecycle — it is never 'loaded, changed, saved again'. Classification: value object, with evidence: no id, value-defined equality, immutable shape."

"Now a hypothetical card. Suppose the team wants a Timezone concept ('America/Bogota'). Question: identity or value? A timezone is a description — a label with rules. Two 'America/Bogota' values are the same timezone. So: value object, and I would keep it immutable with a private constructor. If the AI proposed giving it a UUID 'so it can be stored independently', I would veto it: there is no lifecycle to track."

What I noticed: the decision never came from how many fields the class had or whether it was saved. It came from one question: does this thing have a life, or is it a description?

5 · Guided practice — we do

Three classification questions, with less help each time. Answer before opening the suggestion.

Q1 — worked with me. Is BirthData.vo.ts an entity or a value object?

My reasoning: the file is a .vo.ts — the team's convention for value objects. The constructor is private, creation goes through create() which validates invariants, and there is no identity-based equals(). Classification: value object — with one honest nuance: the record carries an optional id used for persistence, but that is a storage key, not proof of identity (Lesson 05 will dig into that).

Answer 1 — check after you try

Value object. Evidence: .vo.ts naming, private constructor, validated creation, value-based equality. The optional id is a persistence key — note it, but do not let it change the classification yet.

Q2 — half-worked. Is NatalChart.vo.ts an entity or a value object?

Starter of the reasoning: read the top of the file and the create() method. Ask: what identifies it — a stable id with a lifecycle, or the values it holds (planets, angles, houses)? Then finish the thought: CONTEXT.md even says the Chart "is not persisted" and is calculated on the fly…

Answer 2 — check after you try

Value object. It is immutable (readonly fields, getters only), validates invariants in create() (≥10 planets, exactly 12 houses), and is ephemeral — calculated on demand, never persisted. A thing with no lifecycle is a description.

Q3 — your turn to finish. Hypothetical: ChartPreferences (house system, zodiac, orbs). The glossary in CONTEXT.md names it, but no value object exists yet. Entity or value object?

Start: preferences are a set of calculation options — a description of how to compute. Complete the last step: two sets of the same preferences are interchangeable, so ChartPreferences would be a ______, and the honest map says it is currently ______ in the codebase.

Answer 3 — check after you try

Value object. It is a pure description of options, so it should be immutable and value-compared. And the honest map: the glossary names it, but there is no ChartPreferences.vo.ts yet — mark it as an absent concept instead of inventing code.

7 · Feedback + wrap-up

You should now be able to say:

  • "User is an entity — identity by id; the .vo.ts files are value objects — equality by value."
  • "A class keyword or a database row does not make an entity; a lifecycle does."
  • "I can veto 'add a UUID to Email' with identity/equality reasoning, not intuition."

Where the person/money analogy breaks (recap): identity is a choice in code, not a fact of nature; and real bills have serial numbers — the discipline is refusing to track them for things without a life.

Next lesson: entities and value objects often change together — we draw the boundary that protects that group (aggregate and aggregate root).

Spaced question to remember: "Does this object have a life, or is it a description? — That question, not the folder, decides entity vs value object."

AI Drill — try it with the AI

Ask your assistant: "Should we give Email a UUID so it can be stored independently?" Accept or veto using identity/equality — not intuition. The answer should say: Email is a value object (equality by value, no lifecycle), so a UUID would turn a description into a tracked identity for no business reason. If the AI says "it's safer for the database", veto it with evidence: the database key is a storage detail; identity belongs to things that live and change.
