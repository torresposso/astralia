Protecting consistency: aggregate and aggregate root

Some objects must change together, and one object must guard the door. This lesson turns "is this an aggregate?" from a guess into an evidence question.

1 · Hook — a question before any jargon

You are at the supermarket with a cart. Can you reach into the cart, grab the milk, and change its price yourself? Of course not — the price, the quantity, and the total must stay consistent, and the store guards that. The cart is not a pile of loose items; it is a unit: you add items, the total updates, and the cart refuses impossible states like a negative quantity.

Software has the same need. Some objects must change together or the business is corrupted — and somebody has to guard the door. DDD calls that group an aggregate and the door its aggregate root.

By the end of this lesson you will be able to say, with evidence, whether Astralia's BirthData is an aggregate root — and veto AI proposals that call any persisted value an aggregate.

3 · The concept in small steps

New words this lesson: 3

  • Aggregate — a group of objects that change together as one consistency boundary.
  • Aggregate root — the identity-bearing entry point; outside code changes the group only through it.
  • Consistency boundary — the line inside which invariants must hold together.

Recycled: invariant (Lesson 01) and entity/value object (Lesson 04).

Step 1 — The aggregate: one unit of change

In plain words: an aggregate is a group of objects that must change together, like one single thing.

Precise definition: an aggregate is a cluster of associated objects treated as a single consistency boundary: invariants apply to the whole cluster, and the cluster changes as one unit. It is not a folder, a database table, or every object that shares a noun.

The analogy — the checkout cart: the cart, its items, prices, and quantities change as one unit. You do not reach into the cart to change a price — you ask the cart. The cart refuses impossible states (negative quantity) — that is invariant enforcement.

Where this analogy stops being true

A cart is a physical container: the items are literally inside it. In code, the aggregate boundary is a rule, not a container — related classes can live in different files and still belong to one aggregate, and classes in the same folder can belong to different ones.

What is an aggregate?

Step 2 — The aggregate root: the one door

In plain words: the aggregate root is the single door into the group — nobody touches the parts except through the root.

Precise definition: the aggregate root is the identity-bearing entry point of the aggregate; outside code must interact with the group through it, never by changing interior objects directly.

The analogy — the castle gate: visitors enter the castle only through the gate; guards inside enforce the rules. The root carries identity (the castle's name) and the guards enforce invariants (no invaders). Alternatively, think of a tree: the trunk is the only way in; branches and leaves change through it.

Where this analogy stops being true

A castle gate is obvious and physical; in code, nothing prevents a careless import from touching an interior object directly. The root is a convention protected by discipline and tests, not by walls.

Why must changes go through the root?

Step 3 — Errors versus warnings

In plain words: an invariant failure is an error — the change is rejected. A warning is a notice — the change succeeds, but with a flag.

Precise definition: an error means the boundary refused the operation because an invariant would break; a warning means the operation completed but an important condition deserves attention. Confusing the two changes behavior silently.

The analogy: a checkout. If you try to buy a negative quantity, the register refuses — error. If you buy the last item in stock, the cashier says "only one left" — warning: the sale still happens. In Astralia, a nonexistent local time (DST gap) is an error (NonexistentTimeError); an ambiguous time is a warning (dst-ambiguous), and a missing birth time produces the whole-sign warning.

Where this analogy stops being true

A cashier's warning is spoken once and forgotten. Code warnings travel with the result (Astralia returns WarningCode[]), and they must be mapped to the user — if nobody reads the warning, the user never learns their houses are approximate.

4 · Worked example — I do

The AI drill at the end will ask me to "turn BirthData.vo.ts into an aggregate root". Before I can judge that, I need evidence. Read with me three files: src/domain/birth/BirthData.vo.ts, src/domain/birth/ports/IBirthDataRepository.ts, and src/application/birth/SaveBirthData.ts.

"First I ask the four aggregate questions. What must be valid together? Everything BirthData.create() checks at once: date range, coordinates, timezone, plus the DST policy in SaveBirthData. That is a real consistency cluster. What has identity across saves? The persisted record has an id — but the file is a .vo.ts with a private constructor and no identity-based equals(). Who controls changes? SaveBirthData orchestrates, but it is an application service, not a domain root. What does the repository load/save? Whole BirthData records."

"Now the crucial honest conclusion. BirthData.vo.ts is a Value Object by its code convention — it is not automatically an aggregate root. IBirthDataRepository is evidence of a persistence port, not proof of a root. The persisted birth-data record is a candidate boundary only if identity and lifecycle can be demonstrated — and today, that demonstration is missing."

What I noticed: a repository makes an aggregate plausible — something is being persisted as a unit — but it does not prove a root. Proof needs identity, lifecycle, and invariants owned by one domain object.

5 · Guided practice — we do

Three questions toward the aggregate boundary card, with less help each time. Answer before opening the suggestion.

Q1 — worked with me. What must be valid together for a birth data record in Astralia?

My reasoning: I read BirthData.create() and SaveBirthData. A record is valid only when the whole cluster passes at once: date between 1800 and today, latitude -90..90, east-positive longitude, valid IANA timezone, and the UT conversion gate — a nonexistent local time is rejected, an ambiguous one warns. Those validations belong to one boundary, so this cluster is a candidate aggregate.

Answer 1 — check after you try

The invariants enforced together in BirthData.create() plus the DST policy in SaveBirthData: date range, coordinates, timezone, and the nonexistent/ambiguous UT gate. That is the consistency cluster.

Q2 — half-worked. Does the existence of IBirthDataRepository prove an aggregate root?

Starter of the reasoning: the repository is a persistence port — it says "records are loaded and saved". But a root needs identity, a lifecycle, and owned invariants. Complete the thought: a port proves a ______ boundary, not a ______ root.

Answer 2 — check after you try

No. The port proves a persistence boundary — something is stored as a unit. It does not prove a root: identity and lifecycle have not been demonstrated. Repository evidence alone is exactly the trap the AI drill targets.

Q3 — your turn to finish. Are whole-sign and dst-ambiguous errors or warnings, and how do you know?

Start: look at the return type in SaveBirthData — the output is { ok: true; data; warnings }. Now complete the last step: because the save still succeeds and the codes travel inside a ______ array next to ok: true, they are ______ — whereas a nonexistent local time returns ok: false, so it is an ______.

Answer 3 — check after you try

Warnings. The save succeeds with ok: true and returns them in warnings: WarningCode[]. A nonexistent time returns ok: false with an error — that is the error case. The type signature is the evidence.

You should now be able to say:
