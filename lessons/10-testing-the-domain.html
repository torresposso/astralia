Testing the domain: the brake test bench

You would not prove a brake works by driving into traffic — you bench test the part. Domain tests do exactly that for business rules.

1 · Hook — a question before any jargon

An airplane is certified with test benches: the engine is bolted to a stand and run through every scenario — cold, hot, failure — before it ever sees a runway. Nobody discovers the engine's stall behavior by flying a full plane with passengers.

Domain tests are the engine bench. They call the business rules directly — no HTTP, no database, no browser — and prove the rule under every scenario. This lesson shows you Astralia's test bench and the rule Protean warns about: the domain is usually the least tested layer.

By the end of this lesson you will be able to classify any test in Astralia, add a domain test case on paper, and veto test suites that only exercise the domain through the HTTP pipeline.

3 · The concept in small steps

New words this lesson: 4

  • Unit test — exercises one behavior in isolation, with plain inputs and no frameworks.
  • Integration test — exercises several parts together, including a real adapter (DB, HTTP).
  • Test ladder — identify → modify → create: climb from reading tests to writing new ones.
  • Given / When / Then — the universal test shape: arrange, act, assert.

TS basics — unit vs integration

A unit test calls one piece of code directly with plain inputs: a function, a VO, a use case — no framework in sight. An integration test runs several pieces together with real adapters: repository plus Turso, route plus server. Same Vitest syntax; different blast radius. The domain's tests should be units.

Step 1 — The test ladder in Astralia

In plain words: three kinds of tests share the repo: unit tests for the domain, integration tests for the adapters, and an architecture test that polices the layers.

Precise definition: the test ladder is identify → modify → create. First you identify which test covers which rule; then you modify a case (change the expected value); finally you create a new case following Given/When/Then.

Classifying Astralia's tests
File Kind What it proves
BirthData.vo.test.ts Unit (bench) the invariant guard, errors, warnings
NatalChart.vo.test.ts Unit (bench) the chart VO's behavior
DrizzleBirthDataRepository.test.ts Integration the adapter against a real DB
tests/architecture.test.ts Layer police every import edge points inward

The analogy — the brake test bench: a car's brakes are proven on a bench with the wheel mounted, spun, clamped — not by driving into traffic. Unit tests bench-test the part; integration tests test the whole car on a track; neither skips the bench.

Where this analogy stops being true

A brake bench has one fixture; test files grow many cases per behavior. And the bench never ships in the car — tests do ship with the code, forever.

Step 2 — The domain is the least tested layer (Protean's warning)

In plain words: when tests only go through the HTTP pipeline, the domain rules get the least coverage of all — because every scenario must cross the whole stack first.

Precise definition: Protean's pattern "testing domain logic in isolation" warns that in layered applications the domain is often the least tested part: teams test routes, repositories, and controllers, and assume the rules are covered. Bench tests are the fix — call the VO or the use case directly.

The analogy — the airplane simulator: pilots train in simulators that recreate every failure — engine fire, wind shear, instrument loss — before flying a real plane. Domain tests are the simulator: cheap, safe, exhaustive.

Where this analogy stops being true

A simulator does not replace a maiden flight; integration tests still matter. And simulators are expensive — domain tests are the cheapest tests in the repo.

How do domain tests run?

Step 3 — Given / When / Then is the universal shape

In plain words: every test is a mini-story: Given (arrange the inputs), When (call the rule), Then (assert the outcome).

Precise definition: Given/When/Then structures a test as arrange-act-assert: set up inputs, invoke the behavior once, check the result. The same shape works for a VO guard, a use case result, or an architecture edge.

The analogy — the recipe (Lesson 07): Given the ingredients, when the cook follows the recipe, then the dish is served. Tests are recipes with a verdict.

Where this analogy stops being true

Recipes are forgiving; tests are not — a single failed assertion fails the build. And recipes have one outcome; tests encode the expected outcome explicitly.

4 · Worked example — I do

I will read two domain tests and one integration test out loud and classify them. Follow the reasoning; you will modify a test case yourself.

  • BirthData.vo.test.ts — unit: calls BirthData.create() directly, asserts errors and warnings, no frameworks.
  • NatalChart.vo.test.ts — unit: exercises the chart VO's behavior on the bench.
  • DrizzleBirthDataRepository.test.ts — integration: runs the adapter against a real DB and asserts the persistence contract.
  • tests/architecture.test.ts — layer police: no unit or integration label, it polices edges.

"First, the bench. BirthData.vo.test.ts imports the VO and calls create() with inputs; it asserts the returned warnings and errors. Given valid data, when create() runs, then ok; given data in a DST gap, when create() runs, then the warning appears. Plain function calls — no Vitest mocks, no HTTP."

"Second, the integration. DrizzleBirthDataRepository.test.ts needs a real database, because it proves the adapter fulfills the port's contract. If it used a fake, it would prove the fake, not the Drizzle code."

What I noticed: the bench tests are the cheapest and most numerous; the integration tests are fewer and slower. The ladder: identify what each covers, modify a case, then create a new one — never delete the bench.

5 · Guided practice — we do

Three ladder steps with less help each time. Answer before opening the suggestion.

Q1 — identify, worked with me. Which test would prove "BirthData rejects a nonexistent local time"?

My reasoning: that is a rule inside the VO. The bench test calls BirthData.create() directly and asserts the error. The integration test would only prove the rule survives a round trip — slower, no extra truth.

Answer 1 — check after you try

The unit test in BirthData.vo.test.ts — the rule lives in the VO and is bench-tested there.

Q2 — modify, half-worked. Open BirthData.vo.test.ts and find a case for the DST gap. Complete the thought: the test arranges data in the gap, acts by calling ______, and asserts the ______. On paper, write what you would change if the gap behavior changed.

Answer 2 — check after you try

The test arranges gap data, acts by calling BirthData.create(), and asserts the expected error/warning. A behavior change means changing the expected value in the test — on paper, that is the modify step of the ladder.

Q3 — create, your turn to finish. Write a new test case on paper in Given/When/Then for a rule you choose.

Start: pick a rule from Lessons 05-09 — the invariant guard, the DST policy, or the converter gating. Complete the shape: Given ______; when ______; then ______. State which file would host the new case.

Answer 3 — check after you try

Any valid rule with the three clauses — e.g., Given birth data in an ambiguous local time; when create() runs; then the warning includes dst-ambiguous. The new case belongs in BirthData.vo.test.ts (or the corresponding domain test file), never only in an integration test.

6 · Independent practice — you do

Climb the ladder fully on paper. Reopen BirthData.vo.test.ts and tests/architecture.test.ts, then fill the card in your notebook. Do not edit the repository.

Tangible win

A completed ladder card plus two green test runs — the proof you can identify, modify, and create domain tests, and know why the bench matters.

7 · Feedback + wrap-up

You should now be able to say:

  • "Unit tests bench-test the domain with plain inputs; integration tests prove adapters; the architecture test polices the layers."
  • "The domain is the least tested layer when tests only go through HTTP — bench tests are the fix."
  • "Every test is a Given/When/Then story, and I can climb the ladder: identify, modify, create."

Where the brake bench analogy breaks (recap): benches never ship in the car — tests ship with the code. And the bench does not replace the maiden flight: integration tests still matter.
