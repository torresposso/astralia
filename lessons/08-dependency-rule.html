The dependency rule: architecture as an AI navigation map

The web is a detail. The database is a detail. The business rules are the point — and everything must point toward them.

1 · Hook — a question before any jargon

You are in a theater. The audience sees the stage, the lights, the curtains — a perfect show. Behind the stage, technicians run cables, rig lights, and change sets. Nobody in the audience cares about the cable vendor; they care about the play. If the light vendor changes tomorrow, the play must not change.

Software is the same: the user sees the web page; behind it, HTTP routes, a database, third-party services. When the database vendor changes, the business rules must not change. This lesson gives you the rule that makes that true — and shows you the test that proves it.

By the end of this lesson you will be able to place any file in its layer, draw its import edges, and use the architecture test as an AI navigation map.

3 · The concept in small steps

New words this lesson: 5

  • Dependency rule — source code dependencies point inward, never outward.
  • Dependency inversion — outer layers depend on abstractions the inner layers own, not on concrete outer code.
  • Layer police — the test (or linter) that catches a forbidden import at CI time.
  • Onion architecture — the model of layers around the domain, each able to see only the layers nearer the center.
  • Composition root — the one place where adapters get wired to ports.

TS basics — imports are dependencies

An import statement is a dependency arrow: if signin.ts imports SignIn.ts, then signin.ts depends on SignIn.ts. The dependency rule is a rule about where those arrows may point — a policy on the import keyword.

Step 1 — Four layers, one direction

In plain words: Astralia has four layers — Interface (pages and API routes), Infrastructure (DB, auth, external APIs), Application (use cases), Domain (business rules) — and every dependency arrow points inward, toward the domain.

Precise definition: the dependency rule states that source code dependencies must point only inward: Interface → Application → Domain, with Infrastructure also depending only on the Domain ports it implements; the Domain imports nothing from the other layers.

The analogy — the onion: the domain is the core; each outer layer may see the layers inside it, but the core never sees the skin. Astralia's layers: Interface (the skin), Infrastructure (the flesh), Application (the onion's inner layer), Domain (the core).

Where this analogy stops being true

An onion has no tests; Astralia's layer police (tests/architecture.test.ts) verifies the edges at CI time. Also, an onion is a static picture — in code, interfaces let arrows point inward while the actual call flow (route → use case → port → adapter) runs outward. That trick is dependency inversion, Step 3.

Which direction may dependencies point?

Step 2 — Four layers in Astralia, with real files

The four layers and their real inhabitants
Layer What lives there Astralia examples May import
Domain Business rules: entities, VOs, ports, warnings BirthData.vo.ts, NatalChart.vo.ts, IBirthDataRepository.ts nothing from other layers
Application Use cases that coordinate one goal SaveBirthData.ts, SignIn.ts, CalculateChart.ts Domain only
Infrastructure Adapters implementing domain ports; DB, auth, external APIs DrizzleBirthDataRepository.ts, BetterAuthRepository.ts, CaelusBirthConverter.ts, CaelusChartCalculator.ts Domain ports (and frameworks)
Interface HTTP entry points, pages, components src/pages/api/birth-data/create.ts, responseMapping.ts Application (and Domain VOs for shaping)

The analogy — the orchestra conductor (from Lesson 07): the domain is the score (immutable meaning), the application is the conductor (ordering), the infrastructure is the instruments (noise and metal), the interface is the audience's ears. The score never learns the instrument's brand.

Where this analogy stops being true

An orchestra plays the same score the same way every night; software must evolve as the business does. And a conductor is present for the whole concert — the application layer is not: it is only one consumer of the domain, which also runs under tests without any performance.

Step 3 — Dependency inversion: arrows inward, flow outward

In plain words: the flow runs route → use case → port → adapter, but the imports point the other way: the use case imports the port (domain), and the adapter imports the same port — so the domain knows neither the use case nor the adapter.

Precise definition: dependency inversion means outer layers depend on abstractions that inner layers own. The port lives in the domain; the adapter (infrastructure) implements it; the use case (application) calls it. The domain owns the contract; the details obey it.

The analogy — "the web is a detail" (Uncle Bob): the HTTP request is like the theater's ticket: necessary for the show to run, but not part of the play. If tickets become QR codes, the play does not change.

Where this analogy stops being true

A theater can be dark forever without a show; software with no interface still runs tests and other consumers. Also, "the web is a detail" does not mean "the web is unimportant" — it means the business rules must survive the web's replacement.

What proves the rule at CI time?

4 · Worked example — I do

I will open tests/architecture.test.ts and walk its edges out loud. Follow the reasoning; you will draw edges yourself.

"The test polices the three inner layers today. Domain may import nothing from the other layers. Application may import domain only — never interface or infrastructure. Infrastructure may import domain ports plus the frameworks it needs — never interface or application. And pages? The test does not police src/pages/ yet: a page that imported Drizzle directly would not fail it today. That edge is kept inward by documented policy in docs/architecture.md, not by the test — adding a pages rule would be a good future improvement."

"Now watch the flow I traced in Lesson 07 through this rule: chart/natal.ts (interface) calls CalculateChart.ts (application), which calls IBirthDataRepository and IChartCalculator (domain ports), which are implemented by DrizzleBirthDataRepository and CaelusChartCalculator (infrastructure). Every import arrow points inward; every runtime call runs outward through the ports. If the test passes, the onion is intact."

What I noticed: the architecture test is the executable version of the lesson's diagrams. When an AI proposes an import, I can judge it in one sentence: "does this edge point inward?"

5 · Guided practice — we do

Three placement questions with less help each time. Answer before opening the suggestion.

Q1 — worked with me. Which layer may import better-auth?

My reasoning: better-auth is a framework. Frameworks live in infrastructure, behind ports. So the file that imports better-auth is an adapter — BetterAuthRepository.ts — implementing the domain port IAuthRepository. The route calls the port, never the framework.

Answer 1 — check after you try

Infrastructure only, inside an adapter that implements a domain port. Neither the route nor the use case may import better-auth; they depend on the port.

Q2 — half-worked. Where does a second chart calculator go, and what must stay untouched?

Starter of the reasoning: the contract is the port IChartCalculator in the domain — it stays. Complete the thought: the new calculator is an adapter, so it lives in src/infrastructure/…, implements the same port, and gets registered where? The architecture test edges for this feature….

Answer 2 — check after you try

The new calculator lives in infrastructure as a new adapter class implementing the same IChartCalculator port; it is registered where calculators are wired (the composition root). Port, use case, and interface stay untouched; the architecture test edges remain valid because the port still lives in the domain.

Q3 — your turn to finish. Why is "the web is a detail" good news for an AI that writes code?

Start: the architecture gives the AI a map — every file has a layer and a rule for its imports. Complete the last step: when an AI knows the dependency rule, it stops proposing route files that import ______, and instead proposes ______.

Answer 3 — check after you try

When an AI knows the dependency rule, it stops proposing route files that import Drizzle or other infrastructure directly, and instead proposes use cases and domain ports. The architecture is the AI's navigation map: one sentence — "does this edge point inward?" — resolves most placement debates.

7 · Feedback + wrap-up

You should now be able to say:

  • "Dependencies point inward: Interface → Application → Domain, with Infrastructure implementing domain ports."
  • "tests/architecture.test.ts is the executable layer police, and it proves the edges at CI time."
  • "'The web is a detail' means business rules must survive the web's replacement."

Where the onion analogy breaks (recap): an onion has no executable test, and the real flow runs outward through ports — the diagram is static, the code is alive.

AI Drill — try it with the AI

Ask your assistant to plan a new feature file by file, without writing code — for example: "Plan an 'email change' feature for Astralia: one file per layer, with each file's imports listed." Judge the plan: every import edge must point inward. Veto any plan where a route imports infrastructure, a use case imports a framework, or the domain imports anything from the other layers. Ask for the architecture test's verdict on your shared plan.
